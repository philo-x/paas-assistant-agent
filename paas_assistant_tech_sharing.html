二、 技术篇 (Technology)

AgentScope 1.0 四大核心模块总览

✉

Message 模块

信息流通数据实体。将智能体间的数据交互和多模态介质彻底抽象为统一的 Msg 对象。通过自定义多模态 Content 块结构，原生传递文本、图片、思考轨迹及工具使用流。

⚙

Model 模块

异构模型接入适配器。抹平厂商 API 格式与参数结构差异，实现统一响应结构（ChatResponse）。内置 Formatter 支持角色 prompt 翻译及 Usage 单次费用追踪与钩子统计。

☷

Memory 模块

上下文长短期缓存区。提供短期缓存 InMemoryMemory 和长期检索事实库 LongTermMemory 接口规范，通过双轨操作管理和第三方事实沉淀库（如 Mem0）提供上下文容错与支持。

🛠

Tool 模块

物理界映射与执行箱。负责提取方法的 JSON Schema。集成远程 MCP Stateful/Stateless 客户端，引入 Tool Group 分组管理机制，支持程序动态控制可用工具集范围。

二、 技术篇 (Technology)

核心模块 1 - Message 与 ContentBlock 多模态推理轨迹

✉ Message & ContentBlock 架构设计

在多 Agent 的 A2A 交互及流式输出场景中，大模型生成的输出不仅仅包含简单的“回复文本”，还承载着内部的思考链路（Thinking）以及工具调用（ToolUse）。

  • Msg 实体定义: 统一的包装类，包含 name（发送方智能体名称）、role（user/assistant/system 身份）、metadata（辅助元数据）和 content。
  • ContentBlock 抽象设计: content 字段设计为 List 序列。
  • Block 子类派生: 包含代表大模型原生思维的 ThinkingBlock，发起调用的 ToolUseBlock，回填工具执行结果的 ToolResultBlock，以及正常的 TextBlock 和 ErrorBlock。
  • 多模态统一表示: 多模态介质及工具状态变化被解耦隔离在独立的 Block 容器中，避免了字符串混杂污染与解析困难。

核心模块 2 - Model 适配 Formatter 转换及调用流

⚙ Model 异构屏蔽与 Formatter 数据翻译

大模型提供商 API 标准千差万别。AgentScope 引入 Model 核心层对模型底层协议、格式器进行深度屏蔽与统一度量。

二、 技术篇 (Technology)

核心模块 3 - Memory 架构与 Mem0 异步高可靠线程池调度

☷ Memory 架构设计与并发异步线程池

内存会话管理和跨会话长期记忆是运维助手必须攻克的两大难关。本系统引入长短记忆双轨架构及隔离线程池技术：

  • 短期缓存 (Short-Term Memory): InMemoryMemory 缓存当前轮次会话。由于推理触发与状态通知为多线程并发访问，内部消息存取强制采用线程安全的 CopyOnWriteArrayList 隔离并发写冲突。
  • 长期记忆 (Long-Term Memory): LongTermMemoryBase 提供事实沉淀能力，对接第三方个性化长期记忆引擎（Mem0 Cloud / Self-hosted）。
  • 异步 BoundedElastic 线程池: 长期记忆提取（LLM 总结与事实存储）响应迟缓。系统在 Hook 触发 PostCallEvent 时，将 LTM 的 record 任务异步提交至 BoundedElastic 线程池（1 工作线程，3 等待队列），若高并发积压则主动丢弃任务，绝不拖慢 Reason 主链路。
  • 容错屏障 (Fault-Tolerance): 所有 LTM 调用均使用 .onErrorResume() 防御机制，网络抖动或服务故障时降级为日志警告，保障核心对话永不中断。
二、 技术篇 (Technology)

核心模块 4 - Tool 架构、有状态/无状态 MCP 及 Tool Group 动态供给

🛠 Tool 架构与 MCP 客户端精细化管理

在 PaaS 场景下，工具不仅执行轻量的 API 查询，还需要维护长生命周期的终端交互状态（如 Pod 文件浏览）。

  • Stateful (有状态 MCP 客户端): 维持持久的长连接会话（Websocket/SSE），适用于跨多次工具调用需要保持 cookie、登录态或 shell 目录路径的场景。
  • Stateless (无状态 MCP 客户端): 事务型短连接设计。工具调用前瞬间连接，获得数据后即刻释放，适用于轻量级日志拉取、事件获取等，大幅节约系统连接数句柄开销。
  • Tool Group 分组解决“选择悖论”: 运维助手注册了近百个只读与变更工具，过多工具描述会造成 LLM 上下文臃肿并显著降低选参准确度。
  • 动态工具激活 (`reset_equipped_tools`): 系统对工具进行逻辑分组（如 browser-tools、k8s-modify-tools）。智能体根据当前所处的认知阶段，调用 reset 方法自主动态切换可用工具掩码，压缩 LLM 搜索空间。
二、 技术篇 (Technology)

自动记忆管理 (AutoMemoryContext) 压缩及卸载原理

✦ 上下文自动压缩与清理流

在多轮次的 Kubernetes 诊断排查中，每次工具调用都会返回冗长复杂的 K8s 资源 JSON/YAML 信息，内存消息队列很容易超出 LLM 上下文窗口限制导致溢出崩溃。

  • 自适应触发 (msgThreshold): 设定消息条数/Token 临界阈值。一旦未压缩的原始消息数量突破此界限，自动在 PreReasoning 阶段拦截并执行压缩流程。
  • 强制保留保护 (lastKeep): 压缩并非全盘丢失。系统将强制抓取并保护最近的 lastKeep 轮原始会话不作处理，确保大模型拥有精准的最近指令语境。
  • 模型摘要 offload: 调用背景 LLM 对阈值前所有的历史长消息流进行语义归纳总结，凝练为高信息密度的简短 Summary 节点，将原始庞大历史移入冷存储。
  • ContextOffloadTool 兜底: 自动将冷存储检索工具载入智能体工具箱，使得 Agent 在后续推理中如果急需查询历史资源快照，能够通过工具显式检索找回。
三、 经验篇 (Experience & Lessons Learned)

前端思考过程 (Thinking) 模块设计与交互时间线

✦ SSE 流式状态重组设计

在长轨迹诊断任务中，Agent 会多次调用大模型推理和工具。如果前端在等待大模型响应的几十秒内处于白屏或简单 Loading，用户体验将极度糟糕。

  • 结构化 SSE 事件分发: 将数据流划分为 reasoning_delta（推理文本增量）、tool_start（触发工具，返回 Summary 与 Title）、tool_result（工具输出与最终状态）和 error（故障抛出）。
  • ThinkingTimelineStep 状态表示: 前端维护一个由 `sequence` 排序的响应式时间线步骤列表。分为 reasoning、tool、handoff、error 四种角色。
  • 交互流式自动管理: SSE 流入新段落时，自动在页面滚动，并将状态标为 `pending`。识别到 handoff（代表 Agent Gateway 路由子 Agent）时自动创建转移步骤。
  • 动态折叠体验: 推理进行中卡片默认开启并流式打字，一旦收到 A2A 交互 `done` 事件，代表整个诊断执行完毕，时间线卡片自动平滑收缩，提供极其优雅清爽的界面。

三、 经验篇 (Experience & Lessons Learned)

异构 LLM 侧私有控制 Token 双端正则过滤机制

⚠ 痛点：大模型流式输出的“异构私有 Token 泄漏”

当后端代理接入不同的异构模型（如通义千问 Qwen3.6-Coder、DeepSeek-R1 / V4 等）执行流式输出时，大模型在进入思维链或调用工具时，API 报文中会裹挟各种原生私有控制 Token（Qwen 的 <tool_call>、DeepSeek 的 <｜tool▁sep｜>、以及各模型的 <|im_start|>、<|begin_of_sentence|> 等）。这些裸 Token 直接泄露在 UI 上会造成页面乱码甚至引发 Markdown 渲染引擎崩解。

大模型类型 泄漏控制 Token 样本 Java 后端 & JS 前端双重正则清洗模式 净化结果
DeepSeek-R1 <think> / </think> /(?s)<think>.*?<\/think>/g (提取或剥离) ✓ 纯净文本
Qwen 3 Coder <tool_call> / <tool_response> /(?s)<tool_call>.*?<\/tool_call>/gi (剥离 ReAct 语法) ✓ 无格式残留
DeepSeek-V4 <｜tool▁calls▁begin｜> / <｜tool▁sep｜> /<｜[^>]+｜>/g (匹配全角管道控制符) ✓ 清洗彻底
通用 Chat 模型 <|im_start|> / <|im_end|> / <|endoftext|> /`?<\s*[|｜]?(?:im_(?:start|end)|endoftext).+>`?/gi ✓ 无控制符泄漏
双端防御策略：在 Java 后端 ToolNarrator.cleanLlmTokens() 进行第一道清洗，降低网络传输负荷；前端 thoughtsTimeline.ts 在接收 SSE chunk 的流式打字中进行第二道防护，保证最终输入渲染引擎的文字绝对可控。
三、 经验篇 (Experience & Lessons Learned)

两阶段受控变更执行安全防线 (Safety First)

⚠ 痛点：不受控制的 AI “自动修复灾难”

在运维场景中，让大模型直接拥有自主对集群执行 DELETE 或 PATCH 变更的权限是非常高危的。模型幻觉可能会引发误删核心 Deployment 等灾难。

  • 两阶段协议隔离 (Two-Phase Protocol): 任何涉及修改集群状态的动作，必须物理隔离为“生成计划”和“确认执行”两个阶段。
  • 阶段一：change-plan-*(生成计划): Agent 不做实质更改，通过 MCP 获取配置后生成变更草案，在 MySQL 落库生成唯一的 approval_id，并同时返回目标资源、影响评估和回滚预案提示(Rollback Hint)。
  • 等待显式授权: 前端解析到 approval 信息，挂起会话并弹出授权对话框。必须由值班运维人员（User）明确确认。
  • 阶段二：change-execute(批准执行): 必须带上 approval_id 和 confirmed=true 才能解锁平台 MCP 的写通道。执行状态、审批记录、回滚指示在 MySQL 全程落库审计。
三、 经验篇 (Experience & Lessons Learned)

经验篇：MCP Tools 与 SRE Skills 协同设计

🛠 MCP Tools 分组与 SRE Skills (SOP) 双轨协同

在复杂的智能运维场景中，如果让 Agent 直接在裸接口层进行盲目摸索（LLM 盲目猜参数、滥用 kubectl），不仅会导致决策空间指数级膨胀，还会带来高危的系统变更风险。

  • 原子 MCP 工具分组 (Security Boundaries): 遵循 SRE 最小特权原则。在 McpToolRegistrar 中将工具抽象为 K8sGpt、Kom、Groups 等静态常量子组。如将高风险的 list_files_in_k8s_pod 移入默认禁用的“容器交互”组，将 raw kubectl 兜底工具默认关闭，减小故障半径。
  • 专家级 SRE Skills (SOP 排查树): 在 resources/skills/ 下以 YAML 声明 + Markdown 流程的规范，沉淀 pods_diagnosis、kubectl_query 等 8 大领域 SOP。让 Agent 加载预定义知识库，注入诊断判断树（如根据退出码 137 判断 OOMKilled）。
  • 动态掩码缩小搜索空间: 在运行中，Agent 能够根据所处的诊断阶段，自动触发 reset_equipped_tools 方法重新设置可用工具掩码，将 LLM 猜工具的搜索空间压缩到极致，大幅降低 Token 延迟与幻觉。
  • 声明式 Scope 控制 (只读限制): Skills 规范中显式约定 scope: read-only。把所有的查询/诊断等只读 Skill 与实际执行写动作的两阶段受控变更解耦，确保逻辑合规可审计。
四、 结语与展望

总结与展望：迈向生产级智能运维

✔ 成果回顾

  • 高安全性保障: 利用两阶段协议与审计落库，解决大模型直接控制物理基础设施时的风险失控痛点。
  • 极佳交互体验: 重构 SSE 协议输出机制，配合前端响应式时间线，实现思考链（Thinking）的可视化。
  • 异构防御底座: 通过 Java 与 JS 双端对特有 tokenizer Token 联合 Regex 净化，保障前端界面无乱码。
  • 精细长短记忆: 短期高并发安全内存会话搭配长期 Mem0 异步线程池调度事实库，赋予 Agent 跨会话的记忆延续能力。

☄ 展望与演进方向

随着 PaaS Agent 系统的进一步成熟，未来的核心聚焦在更高的复杂度和更强的弹性：

  • 多 Kubernetes 集群协同路由: 引入更复杂的多集群寻址和流量路由策略，实现跨集群的问题快速检索与故障自愈。
  • 大模型驱动的自动化回滚 (Auto-Rollback): 执行变更后，智能体能够对应用健康度自主执行健康监测（Check-loop），诊断不合格则自动触发回滚。
  • 多租户数据与策略物理隔离: 支持在多租户、高安全层级场景下的权限受控隔离。
